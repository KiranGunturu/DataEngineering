region server
=============
- 4 data nodes we can have 4 region server. one running on each data node.
region
=======
each region server can hold multiple regions.
data sorted based on row keys.

memstore
===========
for each region there is a memstore for every column family.
meaning memstore is per column family.

whenever we want to write new records.
consider we are inserting one record.
if we are inserting 100000 times and for each insert if it creates a new file then there will be 100000 files.
these inserts will first goto the memstore (memory) then the size of the memstore goes to a threshold size then the
content of memstore will flush to disk and new file will be created.
this file which is created from memstore to disk is called a Hfile

wal
====
write ahead lock (stored on disk)
consider data is still in memstore(memory) and the server crashes then data is lost
the data loss is tackled by wal.
meaning whenever we write, we are writing to wal then to memstore.
if something crashes, then we can replay wal to get the data back.

block cache
===========

whenever we read the data, the data is cached in memory.
for the next reads it might get the data directly from cache and this will save lot of time.
wal and block cache is one per region server

Hfile
=====
stored in HDFS
immutable
default block size is 64KB


zookeeper
==========
it is a coordinating service for various distributed systems
every server will send heartbeat to zookeeper. also zookeeper will hold the location of metatable.

hmaster
=======
hbase is a master slave arch
hmaster is the master and region servers are the slaves
hmaster will assign regions to region server.
it performs admin activities like ddl operations such as creating or deleting a table.

compactions
============

flushes from memstore to the HDFS create multiple HFiles, especially during periods of heavy incoming writes. which leads to
two major problems.

1. read efficiency gets low. this is because large number of disk seeks needed to process large no of files thereby adversely 
impacting the read peformance
2. it leads to dirty data. A large number of HFiles might result in a lot of redundancy and inconsistency in data.

compaction takes care of this.

two types
minor
where many small files are compacted to few large files
major
all HFiles of a store are picked and rewritten into a single large Hfile


update operations
=================
updates are done using timestamps
designation
VP - timestamp1
SVP - timestamp2

new record is inserted as update.

hdfs is a read only system and changes cannot be made.

Hbase delete operations
=======================

delete is a special type of update in Hbase
where the values for which the delete request is submitted are not deleted immediately.
Rather, these values are masked by assigning a tombstone marker to them.
every request to read these values (with tombstone markers) retuns null to the clinet, which gives the client impression
that the values are alredy delted.

this means with delete, new record is inserted and mask the old record with tombstone marker.


because HFile is immutable.
all the values with tombstone markers are permanently deleted during the next major compactions.
