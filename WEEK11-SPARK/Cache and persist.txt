cache & persist
================

cache does not take any args.

consider if you have a rdd that you have generated by doing bunch of transformations

rdd1

rdd2

rdd3

rdd4.cache

rdd5

rdd5.collect

rdd5.count when this gets called rdd4 will be reused instead recalculating.

cache and persist both have same purpose

if you want to reuse the results of existing rdd then we can use them.

speed up the applications that access the same rdd multiple times.

an rdd that is not cached is reevaulated again each time an action is invoked.

the difference is the cache will cache the rdd in memory (always in memory)



df = spark.range(1,100000).toDF("id") \
		.repartiiton(10) \
		.cache()
		
df.take(10)

spark will always the cache entire partition. -if we cache. 
even though we are taking only 10 records from the partition it will cache entire partition in memory deserialized.

df.count() - with this it will load cache all the partitions

however persist comes with various storage levels

in memory
in disk
off heap

Persist() - if we try to persist without any arguments then it is equivalent to cache.

persist(StorageLevel.MEMORY_ONLY)
===================================

data is cached in memory.
deserialized format

serialized format - bytes format - takes less storage 
deserialized format - objects format - takes more storage



persist(StorageLevel.DISK_ONLY)
================================
data is cached in disk
in serialized format


persist(StorageLevel.MEMORY_AND_DISK) widely used
=======================================

in this data is cached in memory. if enough memory is not availble , then evicted blocks from memory are serialized to disk.

this mode of operation is recommended when re-evaluation is expensive.

and memory resources are scarse.

block eviction:
================

consider the situation that some of the block partitions are so large (skew) that they will quickly fill up the storage memory used for caching.

when the storage memory becomes full, an eviction policy will be used to make up the space for new blocks.

LRU (least recently used)

persist(StorageLevel.OFF_HEAP) 
=================================

blocks are cached off-heap

outside the JVM.

problem with storing the objects in jvm is that it uses garbage collection for freeing up. garbage collection to free up the space is a time taking process.

but this is a unsafe operation as the objects are cached outside of JVM be grabbing a memory from machine instead of executor.

this is more performant as garbage collection is not involved to free up the space.


serialization - increased processing cost but reduces the memory foot print as it takes more storage.

deserialization - processing is fast but uses more memory foot print.

but recommendation is to keep it deserialized and avoid CPU Costs

------------------------------

spark will always store data on a disk in a serialized format (bytes) but when data comes to spark memory it must be deserialized into java objects for spark to work.

deserialized format takes extra space and serialized format is bit compact.

we can save some memory using serialized format but when spark wants to use that data it must be deserialized 

if we try to save some memory - we incur cpu costs.

we can cache it deserialized and save cpu costs and choice is ours but recommendation is to keep it deserialized and save cpu costs.

disk and off heap do not support deserialized format as they always store the data in serialized format.

in memory we can save as deserialized and also serialized by memtioning MEMORY_ONLY_SER but by default it is deserialized.
