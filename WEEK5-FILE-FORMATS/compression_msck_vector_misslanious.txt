================================
Compression Techniques in hadoop
================================
save storage
also it will help us to process the data transfer.
it will reduce I/O costs.


compression and uncompression comes with some cost in terms of time taken to compress and time taken to uncomress.

when we compare it with I/o gains we can actually neglect this additional time.

4 important ones.

1. Snappy
2. lzo
3. gzip
4. bzip2


some of the compression codecs are optimized for storage
however some of the compression codecs are optimized for speed.


trade off

if we want more compression ratio then we have to spend more time in compression.

=========
snappy
=========

very fast compression codec. - speed at which compression happens.

however in terms of compression it is not very good.

optimized for speed rather than storage.

snappy by default is not splittable.

avro, parquet, orc is good combo with snappy as spilittability is already taken care.

=============
Lzo
=============

optimized for speed just like snappy.

lzo is inherently splittable so we can even use with json, xml and text file.

=============
gzip
=============

very good compression performance. better than snappy. 2.5 times better than snappy.

1 gb - 8 blocks

after compression - 2 blocks.

then this means we are not getting the parallesim.


we can ideally reduce the block size so that we have more number of blocks and we get more parallesim.

=============
Bzip2
=============

which is optimized for storage and it is very very slow.

best use would be using hadoop mainly for archival purposes.

--------------------

snappy  - optimized for speed rather than storage, not splittable

lzo     - optimized for speed rather than storage, splittable

gzip   -  optimized for storage rather than speed,
		  in terms of storage it is 2.5 times better than snappy however 2 times slower than snappy in terms of speed. not splittable.

bzip2   - highly optimized for storage, but very very slow, can be 10 times slower than gzip. splittable.

===================
Hive Vectorization 
===================

vectorized query execution is a hive feature that greatly reduces the CPU usage for typical query operations.

A standard query execution system processes one row at a time.

vectorized query execution streamlines operations by processing a block of 1024 rows at a time. 

to use vectorized query execution, you must store your data in ORC format.

by default it is not enabled.

set hive.vectorized.execution.enabled=true;

create table vectorizedtable (state string, id int) stored as orc;

insert into vectorizedtable values ('franklin',1);

set hive.vectorized.execution.enabled=true;

explain select count(*) from vectorizedtable;

now it will show us 

execution mode: vectorized

========================
changing the hive engine
========================

hive supports three execution engines

1. MR - slow
2. tez - fast
3. spark - fastest

MR is the by default.

set hive.execution.engine;
mr


now lets change the engine to spark

set hive.execution.engine=spark;

hive query will leverage the spark engine.

======drop vs truncate vs purge ========

drop -

when we drop a managed table both the data and metadata will be deleted

when we drop a external table then metadata will be deleted. data is not touched.

truncate - 

all the data is deleted. metadata will still be there.

purge -

if purge is set to true , and if we delete the data the data is permanently gone.

but if purge is set to false, then we can recover the data.

blank - ""
null

instead of "" , if we give ABC then all the ABC values will be shown to us as nulls.
