File Formats
===================

why do we need different file formats? why are we even talking about it?

we want to save storage
we want to do fast processing
and we want less time for our I/P operation

our file formats can help us with above 3 if we go with right file format.

there are a lot of choices available on file formats.


1.Faster Reads
2.Faster Writes
3.Splittable (In big data solutions we consider only splittable file formats)
4.Schema evolution support - lets say you created a file and then our schema got changed. is our file format support that or not?
5.Advanced compression. - to save storage. if we have 1TB file then that means it is 3TB including rep factor so storage is matter.
6.Most compatible platform - some files works better works for hive vs spark.

the file formats have been divided into two broad categories.

1. Row based file format 

	-> writing is easy.
	-> Reading is expensive.
	-> compression wont be good as each group is different data types
	
2. Column based file format

	-> writing is expensive
	-> Reading is easy
	-> compression will be good as each group is of same data types.
		ex: all the integers are stored together so whatever the best compression for integers it will apply that.

=====
Avro
=====

Avro is also a row based file format.

it will support faster writes but slower reads in case when we want to read subset of columns.

schema for avro file is stored in json format.

this data is self describing because the metadata/schema is embedded as part of your data itself.

however the actual data is stored in a compressed binary format which is quite efficient.

avro is quite generalized and support processing using lot of preogramming languages like c, c++, java, c#, python, ruby. : language neutral

schema evolution - Avro is quite matured in terms of schema evolution. there is no other file format better then avro.

when avro is best fit?

it is best for storing data in the landing zone of data lake (hdfs) since it is raw data anyone can use and apply processing.

so whenever we do ETL kind of operations then avro is good fit because we have to read all the columns , the entire row.

schema evolution : orc supports schema evolution, but is not as matured as avro.

orc is of 3 parts:

1.Header
2.Body
3.Tail



Header = "ORC"

body : is made up of stripes

even these stripes are furthur divided into block of records by default 10000 rows are there in each row group


body is divided into stripes (by default the size of stripe is 250 MB)

stripes again are furthur divided into row groups and each row group hold 10k rows by default.

consider if orc file is of 500 mb then we will have 2 stripes each of 250 mb

and if in each stripe is of 250 mb then if there are 1 lakh records then this stripe will be furthur divided into 10 row groups.

when we talk about a stripe:
===========================

there are 3 parts

1. set of indexes - max & min & count for each column in every row group in the stripe
stripe1: rowgroup1 empid min 102 max 560
stripe2: rowgroup2 empid min 100 max 780
2. the data itself broken into row groups
3. stripe footer -- tells the encoding used.

Tail:

is made of 2 parts:

1. File footer
contains the metadata at file level and also stripe level
empid min:1 max:83878437
stripe1: rowgroup1 empid min 102 max 560
stripe2: rowgroup2 empid min 100 max 780

2. Post Script
compression is snappy.

the postscript is never compressed by itself and it helps you understand the remaining file.


indexes are at 3 levels:

1. File level
2. stripe level
3. row group level



======================================
Parquet
======================================

it is a colummn based file format.

writes are not efficient but reads are very efficient.

very good for handling nested data.

parquet shares many design goals with orc but it is more general purpose.

compression is at 60% and follows all different encoding techniques mentioned in orc.

it stores the metadata at the end of the file and thats why it is called self describing.

also parquet can support schema evolution to some extent.

it can only support adding or deleting the columns at the end. from middle we can't do.

parquet does not support acid properties but orc does.


three parts:

1.Header - "Par1"
2.Row Group - column chunks -> pages
1 lakh rows -> 
each column chunk can contain for ex 10K rows
3.Footer
metadata and encoding used.


Avro - Kafka
Orc - Hive, Presto
Parquet - Impala, Spark
