spark API execution
	action
	Job
	stages
	tasks
	RDD/dataframe/dataset has partitions
	1 job = 1 or more stages
	1 stage = 1 or more tasks
	Tasks & executors
		1 task is run by 1 executor
		each executor can run 0 or more tasks
	partitions & tasks
		processing one partition = one task
	partitions & executor
		1 partition can stay on 1 executor
		each executor can lead to 0 or more partitions in memory or any disk
	partitions & nodes
		1 executor = 1 JVM on physical node

stages are before shuffle and after shuffle
stages are run in seq order
shuffle - exchange of data between executors
	happens between stages
	must complete before next stage starts
tasks are smallest unit of computation
executed once, per one partition, by one executor

application contain jobs
jobs contain stages
stages contain tasks

dependencies
	narrow - one input(parent) partition influences a single output(child) partition
	fast to compute
	ex: map, flatmap, filter and projections
	wide - one input(parent) partition influences more than one output(child) partition
		involves a shuffle - data exchange between spark executors
		are costly to compute
		ex: grouping, joining,sorting

shuffle
	data exchange b/w executors in the cluster
	expensive because of	
		transferring data
		serialization/deserialization
		loading new data from shuffle files becuase disk is slow

Join optimization
=================
left_semi = all the rows in the left DF for which there is a row in the right DF passing the condition
left_anti = all the rows in the left DF for which there is no row in the right DF passing the condition
above two are only for DFs


why are joins slow?
	data trasfer overhead
	potential OOMs
	limited parallelism

co-loacated RDDs
	have the same partitioner
	reside in same physical location in memory
	can be joined without any n/w transfer
co-partitioned RDDs
	have the same partitioner
	may be on diff executor
	will be joined with nw traffic

shuffled Join
	no partitioner is known
	spark needs to shuffle both RDDs
