each app will have driver

driver - analyze the work, divide the work, distribute the task, schedule task and monitors
executor - execute the code locally on JVM
executors are always launched on the cluster
driver - will run on client machine - client mode
		 will run on cluster machine - cluster mode

In client - mode:
	
		1. when we launch spark-shell automatically spark session is created.
		2. as soon as spark session is created request goes to the YARN RM.
		3. YARN RM will create a container on one of the node manager and will launch and AM for this application
		4. this AM will negoatiate RM for resources in the form of container
		5. RM will create containers on the worker nodes
		6. AM will launch executors in these containers
		7. now the driver and executors can communicate directly
		
	In cluster - mode:
	
		everything is same but the driver runs on the AM which is on the cluster.

what is more preferred? dataframe or dataset
dataframes are most preferred. but why dataframes do not give compile time safety? because 
to convert from dataframe to dataset there is an overhead involved and this is for casting it to a perticular type.
meaning it internally uses serialization - convetting data into a  binary format.
when we are dealing with dataframes then the serialization is managed by tungsten binary format.
when we are dealing with datasets then the serialization is managed by java serialization (slow)
using datasets will help us to cut down on developer mistakes but it comes with an extra cost of casting and expensive serialization.

speculative execution
======================

it happens when one of the task is taking longer time compared to others

spark will run the same task on other node when there is an issue with the worker node like overload , about to crash

it doesn't help in following cases

	data skew
	memory crisis

can be speculative:
	interval-100ms
	multiplier - 1.5 - 1.5 times the median of other tasks
	quantile - 0.75 - if more than 75% of tasks are complete and one task is still running
	minTaskRuntime - 100ms - min time task should run before it is being considered for speculative execution
	
bydefault schedular:
======================

spark runs its jobs in FIFO fashion

. first job gets highest priority
. consumes as much as needed
. then next jobs gets priority once the first one is over.

coalesce & repartition
==========
decrease
avoids full shuffle but always not guaranteed
df.coalesce(5) - it will enforce this 5 to spark.sql.shuffle.partiitions to 5 and join happens in only 5 partitions
df.repartition(5) - it will not enforce this 5 to spark.sql.shuffle.partiitions to 5 and join happens in 200 partitions by default
so repartition is faster than coalesce in this case.

repartition with count - takes more time
coalesce with count - takes less time - no shuffle
