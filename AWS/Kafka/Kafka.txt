controller
===========

if we have single node kafka cluster, it will serve as both a broker and controller

one of the broker from kafka cluster is elected as the controller.

in a kafka cluster there can be just one controller.

controller will perform the following and it will also act as normal broker also

	monitoring of active brokers
	reassigning work when active broker leaves the cluster

which broker is elected as the controller?

the first broker that starts in the cluster becomes the controller

how zookeeper tracks it?

whenever we start the first broker in the cluster, it will create an ephemeral node or an entry in the zookeeper

Kafka/bin/zookeeper-shell.sh

run below which will help us query our zookeeper

./zookeeper-shell.sh localhost:2181

ls - gives us available ephemeral nodes at root level
ls /controller or get /controller- it will display us what broker(broker id:0) is acting as a controller.

if broker node 0 goes down, all the other brokers in the cluster will try to act as controller by creating controller ephemeral node and only one will get succeded.


Kafka-session-9
================

how the partitions of topic are distributed across various brokers?

how to handle fault tolerance?

we have a cluster with 6 brokers

2 racks - group of sys kept in different geographical regions

consider we have a topic with 10 partitions and replication factor of 3

10 * 3 = 30 replicas

how are these 30 partitions assigned to 6 brokers

1.Even disribution (acheiving workload balance)
2.fault tolerance (replicas should not be kept on same machine)

to distribute the partitions across the brokers.. it follows 2 step process

for ex we have 10 partitionss with rep factor as 3

all original partitions are called as leader and replicas are called as followers

leader partitions -   P0,P1,P2,P3,P4,MP5,P6,P7,P8,P9,P10 (replica 1 - origianl)
follower partitions - P0,P1,P2,P3,P4,MP5,P6,P7,P8,P9,P10 (replica 2)
follower partitions - P0,P1,P2,P3,P4,MP5,P6,P7,P8,P9,P10 (replica 3)

1. it creates an ordered list of available brokers

	R1:B0 P0 P6    P5     P4
	R2:B3 P1 P7 P0 P6     P5
	R1:B1 P2 P7 P1 P7 P0  P6
	R2:B4 P3 P9 P2 P8 P1  P7
	R1:B2 P4    P3 P9 P2  P8
	R2:B5 P5    P4    P3  P9

A broker can perform 2 kinds of activities

1. Leader activity - leader partitions
2. follower activity - follower partitions

A leader is responsible for all the requests from producers and consumers

if a producer wants to produce message to kafka topic ..

the producer will request one of the broker in the kafka cluster and get the topic metadata

this metadata will contain a list of all leader partitions of that topic

po - ip1:9092
p1 - ip2:9093
p2 - ip3:9094

so producer will directly send message to leader partitions

once the message is produced.. the leader broker will send an ack

consumer also reads from leader partitions.


Kafka-session-10
================

follower partitions do not serve the producer and consumer request.

followers copy the message from the leader and try to stay upto date with the messages

a follower always wants to be in sync and upto date.

the aim of the follower is be elected as a leader when current leader fails or dies..

followers might lag behind because of many factors

1. n/w congestion
2. broker failure (broker where follower partition kept)


ISR - in sync replicas

zookeeper maintains the list of ISR - this list is maintained by leader broker.

if the follower is not too far.. the leader will add the follower to the ISR list.

how do we define not too far..?

default value is 10 seconds..

consider a scenario where you have ..

1 leader and 2 follower

both the followers are 12 secs behind

in this case, ISR list will be empty. if leader goes down which follower will become the next leader?

if we select any of the follower we miss the latest 12 secs messages..

to tackle this scenario, there is a concept

1. commited versus uncommited messages
2. minimum in sync replicas

if the message is succcessfully copied across all followers then message will be marked as commited

leader partition - at any point of time, there wil be both commited and un-commited messages

if the leader fails, the commited messages are already taken care but the un-commited messages will be lost.

un-commited messages can be resent by the producer.

producers can choose to receive an ack of sent messages only after message is fully commited.

producer waits for ack 

if producer do not get an ack till time-out interval then it will resend the message.

lets say we have 3 partitions and 2 follower partition go down

then single leader partition has the data and is in sync. - but it is very scary situation as we have the data only on one leader partition

kafka protects this by setting minimum number of in-sync replicas of a topic

min.insync.replicas=2

if we do not have atleast 2 replicas in-sync.. the broker will not accept any message.

in this case the leader becomes a read only partition.

Kafka-session-14
================

at least once vs at most once vs exactly once
==============================================

at least - by default
========
IO thread took messages from buffer and sent it to the kafka cluster

the message is stored succcessfully but the IO thread didn't receive ack..

IO thread will again try to send the message as per the no of re try times that we mention in the config.

if the same message is sent again then the message is duplicated.


at most once
=============

if using the producer configuration we set the number of retires = 0 then we get at most once semantics.

here there might be chance that we may loose messages as we are not retrying to send the message where there is an issue.

exactly once
=============
we should not loose any message and we should get message exactly once.

how to acheive it?

enable.idempotence=true

1. each producer will contact the leader broker and it will request for unique producer id.

broker will dynamically assign a unique id to each producer.

2. message seqenence number is generated. start from 0 and increase per partition

each message will be uniquely identified by producer id and seqenence number

this will help the broker to find out duplicates and missing records.

producerid-2 670 "Message 1"
producerid-2 670

Note: it only guarantess for producer retries but it is not valid for duplicates sent by application itself.

Kafka fault tolerant
====================

ability of a system to continue operating without interruption when one or more of its components fail.

each partition is replcated across multiple server for fault tolerance

only one partition will be active at a time called leader

other partition will only replicate message and called followers

the leader handles all read and write request for the partition while followers passively replicate the leader

ex: 3 broker, 1 topic, 1 partiton and 1 replication
