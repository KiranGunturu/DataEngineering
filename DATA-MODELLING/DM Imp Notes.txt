semi additive facts
===================

A semi-additive fact is a fact that can not be aggregated for a certain dimension

account balance is semi-additive on the month dimension; it can be aggregated across months

ex: in july month end cust account balance is 5000
	in aug month end cust account balance is 4500

we can't add these two numbers if I want to get an aggregated balance for both july and aug.

anytime we use this fact, we must either filter to a specific month or we just display data by month

if we do not display or filter by month, we will sum the balance for various months and get an incorrect value.


non-additive facts
===================

we cannot add these facts across any dimension

such as ratios and percentages

a good approach is to store the numerator and denominator values seperately

wherever possible, store the fully additive components of the non-additive measure and sum these
components into the final answer set before calculating the final non-additive fact.

but we can get account balance of all the customers at july month end. this can be done on customer dim.

thats why we call it as a semi-additive fact

confirmed facts
===============
if the same measure appears in seperate fact tables, care must be taken to make sure the technical
defnitions of the facts are identical if they are to be compared or computed together

if the seperate fact dimensions are consistent, the confirmed facts should be identically named; but
if they are incompatiable, they should be differently names to alert the business users and BI applications

ex: auto policy count vs home owners insurance policy count

fact table types
================

transaction fact table //point of sales
======================
ex: sales fact

periodic snapshot fact tables
==============================
a row in periodic snapshot fact table summarizes many measurement events occuring over a standard period, such as a day, a week
or month

the grain is the period, but not the individual transaction

ex: monthly account balance/ activity fact

accumulating snapshot fact tables 
=====================================
revisiting the same record and updating the corresponding date in the record (like order_rcvd_dt,
order_prcd_dt,ship_dt, dlvry_dt) whenever there is a change in the process

helps to business improvement as we can see where is the bottleneck. is it at shipping or packaging

here we dont create seperate date dim for these colmns instead we create one and reuse (rename the date_ky in fact table)- this dim is called role playing dim

this type of fact table is used to show the activity of a process that has a well defined begining and end.

pipeline or workflow process, such as order fulfillment or claim processing, that have a defined start point, standard
	intermediate steps, and defined end point can be modeled with this type of fact table

there is date FK in the fact table for each critical milestone in the process.

ex: activity fact

functional dependency
=====================
is a relationship between two attributes
ex: SSN- birthdate
	VIN - manufacture

ssn is the determinant and bday is the dependent


1NF- eliminate repeating groups and assign PK to each table
ex: medicine1, medicine2,medicin3 or phone1,phone2,phone3
fact about the PK


2NF- whole primary key - all the non-key attributes must be dependent on PK
ex if there is a patient visit table and we are storing all clinic, doctor and patient info in one table
then we need to create seperate entities for all three like patient table, doctor table and clinic table

3NF - nothing but the PK - all non-key attributes should not have any dependency among them and dependency should be only on the PK
after meeting 2NF - we have to make sure we are controlling the redundancy and also if we delete 
one doctor from table it should not impact the other tables.

Age is a great example of a dimension that can also play the role of a metric.

If I ask, “what’s the retention of 29 year olds?” then it’s a dimension.

If I ask, “what’s the average age of people who play Halo 3?” then it’s a metric.

Really depends on if it’s aggregated or in the GROUP BY.

If it’s in the GROUP BY, it’s probably a dimension.
If you’re slapping an AVG, SUM, or MAX around it, it’s probably a metric.
